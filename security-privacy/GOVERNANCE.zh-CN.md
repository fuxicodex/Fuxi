# FuXi 治理、标准与信任

**Governance, Standards & Trust**

*最后更新：2026-09-12 · 版本 1.0*

技术标准，以及我们向用户公布的信任承诺。

## 1. 治理

### 1.1 目标

1. **保护用户** —— 用户隐私、数据与安全是最高优先级。
2. **默认安全** —— 安全是设计原则，而非事后补救。
3. **尊重全球法律** —— 遵守广泛适用的隐私原则。
4. **诚实与透明** —— 只声称可验证的能力；绝不虚构认证。
5. **持续改进** —— 通过评审、度量与事件学习中不断演进。

### 1.2 文档层级

```
入口文档（面向用户）
  隐私政策 · 安全白皮书 · 服务条款
  使用政策 · 数据保护 · 合规与责任

支撑文档
  治理、标准与信任（本文件）
  运营（事件响应、披露、第三方、业务连续性）
```

当下级表述与上级表述冲突时，以上级为准。当本项目的做法与适用法律冲突时，
以法律为准，并更新本项目。

|---|---|---|
| 安全架构与威胁模型 | 安全工程 | 安全负责人 |

### 1.4 评审周期

| 对象 | 频率 | 触发条件 |
|---|---|---|
| 治理与政策 | 每年 | 重大战略、法律或产品变更 |

### 1.5 例外

任何偏离政策或标准的做法都必须以书面形式提交，说明理由、范围、期限与风险；
须经问责负责人书面批准；须记录评审日期；若到期未评审则自动失效。例外不得被
用于规避法律义务或损害用户权利。

## 2. 信息安全政策

**目标**：保护用户与 FuXi 信息的机密性、完整性、可用性（CIA）。

### 2.1 核心立场

FuXi 的安全性来自架构本身，而不是外挂式防御：

- **本地优先** —— 代码、配置、凭据与会话都留在你的设备上。
- **默认不信任** —— 命令、文件与外部输入在使用前均经过校验。
- **显式权限** —— 敏感操作需要批准；不存在隐式提权。
- **最小权限** —— 只授予任务所需的最低能力。
- **可验证** —— 更新经校验和验证；行为可审计。

### 2.2 控制域

| 领域 | 关键控制 |
|---|---|
| 命令安全 | AST 安全分类器 + 规则集 + 权限提示 + 审计日志 |
| 凭据管理 | 仅本地存储于 `~/.fuxi/`，绝不上传；建议设置文件权限 + 磁盘加密 |
| 更新完整性 | SHA-256 验证 + 原子替换 |
| 会话与数据 | 本地存储；用户可随时删除 |
| 账号与注册 | 账号为必需，数据最小化，令牌最小权限 |
| 第三方集成 | 仅加载用户自行配置的 MCP 服务器与插件 |
| 漏洞管理 | 私密报告 + 披露前修复 |
| 日志 | 本地审计日志；日志中不含明文凭据 |

### 2.3 违规处理

违规按影响程度评估，并触发整改、流程修订或事件响应流程。

## 3. 技术标准

### 3.1 身份认证

FuXi 账号为**必需**。在该账号内，有两种连接模型的方式：

| 路径 | 机制 | 用途 |
|---|---|---|
| FuXi 账号（必需） | OAuth 登录（`fuxi login` / `fuxi setup-token`） | 运营账号；开通 FuXi 托管模型 |
| 自带密钥（可选） | API Key / 环境变量 / 本地配置 | 向你所选的提供商进行身份认证 |

**凭据要求**

1. **本地存储** —— API Key 存放于 `~/.fuxi/config.yaml` 或环境变量中，绝不
   上传。
2. **最小暴露** —— 凭据绝不写入日志、错误信息、截图或 issue/PR。
3. **文件权限** —— 将 `config.yaml` 设为仅属主可读（例如 `chmod 600`）。
4. **CI 使用** —— `FUXI_API_KEY` 及类似变量可替代配置文件。

**OAuth 令牌。** `fuxi login` 以交互方式登录（stdin 流程）；令牌仅用于身份认证
与开通托管模型，以最小权限签发，并可通过登出撤销。`fuxi setup-token` 会打印
一个供 CI 使用的令牌，即 `FUXI_OAUTH_TOKEN`。

**提供商身份认证。** 在 BYOK 模式下，FuXi 作为标准客户端将你的密钥提供给
提供商。TLS 与密钥轮换遵循提供商自身的标准。

### 3.2 密码学

| 场景 | 要求 |
|---|---|
| 与模型提供商的通信（BYOK） | 提供商所要求的加密传输（通常为 TLS），由提供商与用户协商 |
| 官方安装/更新下载 | 通过 HTTPS（TLS） |
| 更新完整性 | 在原子替换正在运行的二进制文件之前，先对照已发布的清单进行 SHA-256 验证 |

> 与模型提供商之间的传输加密由**该提供商**实现；FuXi 遵循其标准客户端行为，
> 不自行发明加密协议。

**存储。** 本地凭据与数据由文件系统权限保护。本地文件是否额外加密取决于产品
实现；我们不虚构未披露的加密细节，并建议启用操作系统提供的加密（FileVault、
BitLocker、LUKS）。

**密钥材料。** API Key 与 OAuth 令牌由你或你的提供商生成；FuXi 不生成也不
托管你的提供商密钥。密钥仅存储在本地，既不复制也不上传。

### 3.3 日志与监控

**原则**：在为用户提供可追溯性的同时，绝不在日志中泄露敏感信息。

- FuXi 记录其执行的工具调用与命令操作，存储于**本地**（位于 `~/.fuxi/`；调试
  日志位于 `~/.fuxi/logs/`），不上传。
- **必须记录**：已执行的命令/工具名称；时间戳；结果摘要；权限模式以及用户
  是否批准。
- **不得记录**：明文 API Key 或令牌；用户未主动提供的敏感内容；完整源代码。
- 密钥、令牌与密码均**脱敏**处理（例如 `***`）。分享日志前请先审阅并脱敏
  个人数据。
- **监控是本地的**：`fuxi doctor`（环境）、`fuxi verify`（提供商连通性）、
  `/status` `/context` `/cost`（运行时状态），以及可关闭的后台版本检查。这些
  针对的是你自己的环境 —— 不是对用户内容的服务器端遥测。
- **保留期**由用户控制；删除 `~/.fuxi/` 即清除日志。

### 3.4 安全开发

每次变更都遵循安全生命周期：需求与威胁建模 → 安全设计（默认安全、最小权限）
→ 安全实现（避免 OWASP Top 10 类别，如注入、访问控制缺陷与敏感数据暴露）→
测试（命令分类器与权限模型是关键测试对象）→ 发布前验证（SHA-256 与回归测试）
→ 发布后监控与响应。

**命令安全**是风险最高的攻击面，因此有专门防护：执行前的 AST 分类、拦截
危险模式的规则集、权限提示，以及 `--auto` 上的熔断机制。

**AI 专项安全**

| 关注点 | 要求 |
|---|---|
| 提示注入防御 | 不信任外部内容（文件、网页、MCP 输出）；不盲目执行其中嵌入的指令 |
| 输出验证 | 模型输出并非事实；关键操作需用户确认 |
| 工具调用安全 | 校验工具参数，使恶意内容无法诱使产生危险操作 |
| 权限一致性 | 模型驱动的操作与用户权限模式一致；不得提权 |
| 数据边界 | 只向模型发送完成任务所需的最小上下文 |

## 4. 信任承诺

**一句话**：FuXi 本地优先、自带密钥、凭据绝不上传、你的代码与对话绝不被收集
或保留，并且我们尊重全球法律 —— 这一切由架构实现，而非口号。

| 维度 | 事实 |
|---|---|
| 数据驻留 | 代码、配置、凭据与会话都留在你的设备上 |
| 密钥 | 仅本地，绝不上传或复制 |
| 内容收集 | 不收集代码或对话 |
| 强制注册 | 是 —— 使用 FuXi 需要 FuXi 账号 |
| 内容上传 | 无 —— 零内容上传 |
| 命令安全 | AST 分类器 + 权限提示 + 审计日志 |
| 隐形保护 | 默认开启，无需配置（见[安全白皮书 §5](SECURITY.zh-CN.md)） |
| 更新 | SHA-256 验证 + 原子替换 |
| 遥测 | 无隐藏的后台上传；已披露的分析功能可退出（见[隐私控制](DATA_PROTECTION.zh-CN.md)） |
| 认证声明 | 不虚构第三方认证 |
| 全球法律 | 与主要隐私/AI 法律对齐；风险在[合规与责任](COMPLIANCE.zh-CN.md)中披露 |

**我们坚守的承诺**

1. 默认本地、最小化收集、透明披露。
2. 命令与权限可审计、可控、可撤销。
3. 更新可验证。
4. 不虚构认证，不夸大能力。
5. 面向开发者；不面向不满 14 周岁的儿童 —— 14–17 岁用户需由父母或监护人
   参与；不做行为广告或画像。
6. 诚实说明局限 —— FuXi 是工具，不是顾问；输出可能有误，依赖之前必须审阅。
